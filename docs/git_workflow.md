# Git workflow: от ветки до пуша

Пошаговый процесс работы с задачей: создать ветку, сделать изменения,
проверить и запушить. Пушить напрямую в `main` нельзя — только через ветку и PR.

## 1. Обновить main

Новая ветка всегда создаётся от свежего main, иначе потом будут конфликты:

```bash
git checkout main
git pull origin main
```

## 2. Создать ветку

Название — по номеру задачи в Jira (`OC-XXXX`):

```bash
git checkout -b OC-8417
```

## 3. Работа и коммиты

Коммитить лучше небольшими порциями с понятными сообщениями:

```bash
git status                  # посмотреть, что изменилось
git add <файлы>             # добавить нужные файлы (git add -A — все)
git commit -m "add: api tests for user settings"
```

## 4. Проверки перед пушем

Обязательный минимум — то же самое гоняет CI, лучше поймать локально:

```bash
# Линтер: базовые правила + запрет assert/pytest в pages/
uv run ruff check .

# Проверка Allure-метаданных (@allure.suite / @allure.title / owner)
# — валит запуск ещё на этапе коллекции
uv run pytest tests --collect-only -q
```

Если ruff нашёл автофиксируемые замечания:

```bash
uv run ruff check . --fix
```

И прогнать тесты, которых касались изменения:

```bash
uv run pytest tests/api -q          # если менялись API-тесты/клиенты/модели
uv run pytest tests/ui -q           # если менялись UI-тесты/pages
```

## 5. Запушить ветку

```bash
git push -u origin OC-8417
```

`-u` привязывает локальную ветку к удалённой — дальше достаточно просто `git push`.

## 6. Создать Pull Request

По ссылке, которую git выводит после пуша, либо через CLI:

```bash
gh pr create --base main --title "OC-8417: pydantic models for api tests"
```

После мёрджа PR в main автоматически запускается CI-прогон тестов
с выгрузкой в Allure TestOps.

## Если что-то пошло не так

### Случайно закоммитились в main

Коммиты нужно перенести в отдельную ветку:

```bash
git checkout -b OC-8417      # создать ветку и сразу перейти (коммиты остаются в ней)
git branch -f main origin/main   # передвинуть main к origin, не переключаясь на него
git push -u origin OC-8417
```

Важно: сначала создаём новую ветку и только потом двигаем `main` — иначе коммиты
повиснут без ссылок (доставать придётся через `git reflog`).

### Main ушёл вперёд, в ветке конфликты

Пока вы работали, в main смёрджили другие PR, и ваши файлы пересекаются с чужими:

```bash
# 1. Зафиксировать незакоммиченное (rebase не стартует на грязном дереве)
git add -A && git commit -m "wip"

# 2. Подтянуть свежий main и перебазироваться на него
git fetch origin
git rebase origin/main
```

Git остановится на конфликтах — в файлах появятся маркеры:
`<<<<<<< HEAD` (версия из main) / `>>>>>>>` (ваша версия).
Отредактировать файл, оставив нужное, затем:

```bash
git add <файл>
git rebase --continue        # и так по каждому конфликту
```

Особый случай — `uv.lock`: руками его не мёрджить. Сначала разрешить
конфликт в `pyproject.toml`, затем перегенерировать:

```bash
git checkout origin/main -- uv.lock
uv lock
git add uv.lock
```

Запутались — безопасная кнопка «отмена», возвращает всё как было:

```bash
git rebase --abort
```

После ребейза повторить проверки (шаг 4) и запушить с force:

```bash
git push --force-with-lease
```

`--force-with-lease` (а не голый `--force`) — пуш пройдёт, только если на origin
никто ничего не допушил, пока вы ребейзились.

### Отмена и временное сохранение изменений

```bash
git restore -- .        # откатить незакоммиченные изменения в файлах
git reset --hard        # откатить всё до последнего коммита
git clean -fd           # удалить неотслеживаемые файлы и папки
git stash               # спрятать изменения
git stash pop           # вернуть спрятанное
git stash clear         # очистить stash
```
